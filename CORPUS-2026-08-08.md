# Corpus run, 2026-08-08 — a fresh sample of real scans

A test run over **a new group of Zotero sources**, chosen to be the thing this
app is actually for: printed matter that was **scanned**. Deliberately excluded —
manuscripts and letters (Archive Processor's job), anything photographed by hand,
and anything born-digital.

The pipeline came through it clean. The interesting results are about the
*corpus*, not the code, and they are recorded here because they change what the
project's headline number means.

---

## 1. The old corpus is mostly not scans — and the headline number rests on it

> **Note added 2026-08-15.** Every verdict in this file came from `classify-source`'s **own**
> page-image test, which was a second copy of `Flattener.pageIsAnImage` combining a max over
> five pages with a median over those pages. The tool asks the app's two questions now
> (`BUGS.md` T17), so these rows are **not comparable row by row** with a run made after that
> date; `CORPUS-2026-08-15.md` is the current corpus under the repaired gate. The direction of
> this section's finding is unaffected — the old gate was, if anything, *more* willing to call
> a document a scan, so "mostly not scans" was not an artefact of a strict classifier.

Every document in `testdocs/` classified with `Tools/classify-source.swift`:

| | count | share |
|---|---:|---:|
| **scanned** | **27** | **35%** |
| born-digital | 40 | 51% |
| photographed by hand | 10 | 13% |
| no page image at all | 1 | 1% |

By bucket, the pattern is not random. `newspaperArticle` is 7/8 born-digital
(ProQuest and NYT downloads, not scans). `manuscript` is 6/8 born-digital —
those are *finding aids*, text documents describing an archival collection,
not images of one. `letter` is 5/7 hand-photographed. `book` is 6/8
born-digital.

**This matters because of what is claimed on top of it.** README, HANDOFF and
CHANGELOG all cite:

> 78/78 process successfully, median 100% line-start and line-end selectability,
> median 0.00 text-layer offset, median 100% word retention

That is a true statement about those 78 files. It is a much weaker statement
about *OCR quality on scans* than it reads as, because two thirds of the corpus
either had perfect digital text already (so "word retention" was measuring how
well OCR reproduces text the file could simply have kept) or was a photograph of
a manuscript, which the app is not for.

**To fix:** either re-cite the headline against the 27 real scans, or replace the
corpus. The number below is the honest version for this app's use case.

## 2. The pipeline on 40 fresh scans: clean

Sampled from **1,880 candidate attachments** added to Zotero since 2021-08-08,
of the right item types, none of them already in `testdocs/manifest.tsv`. 800
were classified; 386 came back `scanned`; 40 were drawn stratified by item type
× era, 2 per bucket. **Three pages from each** (at 25%, 50%, 75% of the
document — never page 1, which in a scanned book is the least representative
page there is), giving 118 pages in 78 MB.

| | |
|---|---|
| processed successfully | **40 / 40** |
| line-start selectability | median **100%**, min 98% |
| line-end selectability | median **99%**, min 81% |
| word retention | median **99%**, min 96% |
| text-layer offset | median 0.10, **max 0.10** |
| runs colliding vertically | 12 of 40 documents have ≥1, worst 6.2% |

No failures, no crashes, no lost pages, nothing published that should not have
been. Per item type, median line-start is 100% across all eight types.

## 3. Problems to fix

### P1 · The app silently degrades a born-digital PDF — FIXED 2026-08-08

**The most serious thing this run turned up.** Drop a born-digital PDF on the
window in Searchable PDF mode and the default settings rebuild the pages as
images — throwing away real, correct, embedded text — and replace it with OCR.

Measured on three pages of `Jacobson_2004_Raising consumers.pdf`, a born-digital
book with no page images at all:

| | before | after |
|---|---:|---:|
| characters | 6,237 | 6,128 |
| words | 1,031 | **938** |
| words in the output that existed in the original | — | **86.1%** |

So ~9% of the words are gone and about one word in seven of what remains is an
OCR artefact — `traditiona` for `traditional`, `teshm` for a word that was
perfectly legible in the source. The run reports **success**.

This is not a crash, and the app is behaving exactly as designed: `rebuildImages`
defaults on because *for a scan* an existing text layer is mac-ocr's own and
would double up. For a born-digital file the premise is inverted — the existing
text is better than anything Vision will produce from a rendering of it.

It matters in practice because a real library is full of these: **51% of this
project's own corpus.** Nothing in the UI says a word about it.

**Fixed by asking.** Not refusing: sometimes the embedded text is itself broken
and re-OCRing is the point, so the capability stays and only the surprise goes.
A pre-flight (`Flattener.hasDigitalText`, off the main actor) flags inputs whose
text sits on *no page-sized image* — which is what separates real digital text
from an OCR layer over a scan — and an alert offers **OCR Anyway / Skip Those /
Cancel**, with "Don't ask again" and a Settings toggle. See BUGS.md C17.

**Extract Text mode still re-OCRs these** rather than reading the text out.
Nothing is destroyed — the input is untouched — so it is tracked in TODO.md
rather than here.

### P2 · The documented corpus figures need re-citing — FIXED 2026-08-08

Not re-cited: **replaced**. `Tools/sample-zotero.py` now classifies every
candidate and keeps only scans, and `testdocs/` is 84 documents, all 84 verified.
Measured through the shipped pipeline: 84/84 processed, median 100% line-start
and line-end, median 99% word retention, max offset 0.10, 1.33% of adjacent runs
overlapping. Medians unchanged; the tail is worse and honest. See BUGS.md D1.

### P3 · Line-end selectability has a worse tail than the docs suggest — FIXED 2026-08-08 *(documentation)*

`thesis_mid_DUBIN_The_Development_of_the_Concept_of_Collective_Security` scores
**81%** line-end — meaning nearly a fifth of its lines cannot be selected to
their end. HANDOFF describes the weak spot as "86–95% on 1920s–50s letters and
typescripts"; this is a 20th-century typescript thesis and it is below that
range. Looked at, line by line. Across the full 84-document scanned corpus the floor is
**71%**. Five of six misses on the sampled document are the drawn run stopping
short of the box a *second* OCR pass reports (the two passes disagree about
trailing punctuation); one is vertical, from a superscript inflating Vision's box
height. Documentation corrected; `draw` deliberately left alone — see BUGS.md D2,
including the fix that was written, measured to change nothing, and reverted.

### P4 · Vertical overlap is present in 12 of 40 documents — FIXED 2026-08-08 *(now quoted)*

Up to 6.2% of runs in one document collide vertically. That is the property
CLAUDE.md invariant 3 exists to protect: where invisible runs overlap, Preview
stops treating them as separate lines and a drag-selection runs straight past
one. It is not new and it is not catastrophic, but the corpus figures never
reported it as a headline and it is measurable, so it should be tracked.

Now tracked: **1.33% across the 84-document corpus** — 74 of 5,564 adjacent
pairs, in 23 of 84 documents. Quoted in README, HANDOFF and `manifest.tsv`, so a
`SearchableWriter` change that moves it is visible.

### P5 · Two harness faults, recorded so they are not re-lived

Neither is a product defect; both wasted a cycle here, and both are the same
class of thing this project keeps paying for.

- **18 of 40 fixtures were written without a `.pdf` extension**, so the scoring
  loop's `find -name '*.pdf'` silently scored 22 and reported success. "Scored
  22" looked exactly like "scored everything" until the counts were compared.
- **The scoring loop discarded stderr** (`2>/dev/null`), so when the count came
  up short there was nothing to explain it. Re-running with stderr kept produced
  an empty error file, which is what finally pointed at the filenames rather than
  the code.

## 4. How to reproduce

```sh
# classify anything, one TSV row per file
swiftc -O -o /tmp/classify -target "$(uname -m)-apple-macos13.0" \
  Sources/*.swift Tools/classify-source.swift   # (as main.swift; see Tools/README.md)
/tmp/classify some.pdf                          # -> scanned | born-digital | photographed
```

The sample was drawn with a Zotero query filtering on `items.dateAdded >=
'2021-08-08'` and item types `book, bookSection, journalArticle,
newspaperArticle, magazineArticle, thesis, report, document`, excluding every
path already in `testdocs/manifest.tsv`, then gated on a `scanned` verdict.
`Tools/sample-zotero.py` does the stratification but **does not yet apply the
scanned gate** — that is why the old corpus looks the way it does, and it should
be wired in.
