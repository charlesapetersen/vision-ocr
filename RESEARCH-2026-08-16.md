# How other tools solve the problems this project keeps re-deriving

Read after `BUGS.md`'s header. The question asked on 2026-08-16 was: *are we
re-deriving things other people have already solved?* It was prompted by four
rounds of refused routing thresholds (R56, R57), a constant calibrated by sweep
with no external justification (`reserveEms`), and a C23 fix refused on a cost
that turned out to be avoidable.

**The answer, in one line each:**

| | answer |
|---|---|
| word welding, and what `reserveEms` should be | **solved elsewhere, and it bounds our constant** — §1 |
| the four properties that fight each other | **solved elsewhere, by a different architecture** — §2, and it is not a drop-in |
| whether per-word runs + real spaces retire the class | **no** — the hypothesis is refuted, §2 |
| the crop box through a qpdf merge | **solved, by an option C23 was refused without reading** — §3 |
| R56 / R57, the shape signal | **solved elsewhere; not researched here** — §5 has the order of work |

`sharedInkFraction` is deliberately not on that list: R81 derives it from 852
measured pairs and it does not need outside help.

**Provenance is marked throughout.** `[source]` means somebody read the actual
code and quoted it. `[measured]` means this project ran it. `[observational]`
means a bug report or forum post, not source. `[unknown]` means nobody
established it and it is not to be guessed at. That distinction is the whole
value of this file — CONTRIBUTING §3 is about instruments, and a secondhand
threshold is an instrument.

## 1. Why words weld: the extractors, and the window `reserveEms` lives in

**The finding that matters: our hand-calibrated 0.25 em is inside a window with
computable edges.** It was not undefended before — its doc comment argued that a
proportional reserve clears a proportional threshold at every font size — but the
*number* came from sweeping the corpus, and nothing said what would go wrong above
or below it. Now something does.

Every extractor re-derives word boundaries from geometry. Three of the four are
readable, and their thresholds are all fractions of the font size:

| extractor | inserts a space when the gap is | breaks the line at | honours a real `U+0020`? |
|---|---|---|---|
| **poppler** `TextOutputDev.cc` | ≥ `maxCharSpacing` = **0.03** em, but the *word* splits at `minWordBreakSpace` = **0.1** em | baseline delta > 0.5 absolute; `maxIntraLineDelta` 0.5 em | **No.** The space ends the word and is then *discarded*; the output space is re-derived from `primaryDelta` |
| **pdf.js** `evaluator.js` | `TRACKING_SPACE_FACTOR` = **0.102** em; nothing below `NOT_A_SPACE_FACTOR` = 0.03 em, *even if a space is in the stream*; span breaks past 0.6 em | vertical shift > 0.25 × height; advance < −0.2 em | **No.** Whitespace is dropped before the heuristic unless the caller passes `keepWhiteSpace: true`, which a producer cannot control |
| **mupdf** `stext-device.c` | `SPACE_DIST` = **0.15** em; **two** spaces past 0.3 em; nothing past `SPACE_MAX_DIST` 0.8 em | `BASE_MAX_DIST` 0.8 em off baseline | **Yes.** Space glyphs go through `add_char_to_line` like any other |
| **PDFKit** | **[unknown]** — closed, and no threshold was established | **[unknown]** | **[unknown]** |

`[source]` for the first three, quoted from current upstream.

### What follows, and it is the useful part

**A real space character is necessary but not sufficient.** poppler consumes it
as a word terminator and then decides independently whether to emit one, from
geometry alone. pdf.js discards it earlier still. So "just write spaces" — the
obvious reading of PDF 32000 §14.8.2.5, which poppler's own maintainers cite —
does not make word breaks safe. **Only the drawn gap does.**

That gives `reserveEms` its first derivation:

```
lower bound   max(poppler 0.1, pdf.js 0.102, mupdf 0.15)  = 0.15 em
upper bound   min(mupdf's double-space trigger 0.3,
                  pdf.js's span break 0.6,
                  poppler's column gap ~1.0)              = 0.30 em
```

**0.25 em sits inside (0.15, 0.30) with margin on both sides.** The constant was
right; it was arrived at by sweeping the corpus and it happens to land in the
window the three readable extractors define. That is now written on the constant
itself, and it converts a calibrated number into a bounded one — the difference
between "it scored best" and "below 0.15 poppler and mupdf stop seeing a word
break, above 0.30 mupdf starts emitting two spaces".

**PDFKit is the one that matters most to us and the one nobody can bound.** It is
also the extractor named repeatedly upstream as the worst-behaved:
*"Apple's viewer is notorious for this"* — Tesseract's PDF renderer author, on
words running together `[observational]`. Our own instruments measure PDFKit
directly, which upstream never has; see §4.

## 2. Tesseract's text layer: the architecture, and what we get wrong

`[source]` — `tesseract/src/api/pdfrenderer.cpp`, current `main`.

| | ours | Tesseract |
|---|---|---|
| granularity | one run per **line** | one show-op per **word**, `Td` per word from the previous word's *origin* |
| word spacing | intra-run text; the reserve holds the gap to the next fragment | a real `U+0020` appended to every word, since 2019 |
| width fit | **the font size** is chosen so the natural advance matches the box | **`Tz`** — horizontal scaling — is chosen so the advance matches the box |
| vertical extent | a squash in the text matrix, to undo the height the width fit forced | **the font size**, straight from the recogniser. **No vertical scaling anywhere** |
| the font | Helvetica, real glyphs | a **glyphless, fixed-pitch** font (`/DW 500`, every CID → one blank glyph) |

### The one architectural finding

**Tesseract has two independent knobs where we have one.** `Tf` owns the vertical
extent and `Tz` owns the horizontal fit, and the two do not interact — in their
arithmetic the font size cancels out of the width fit entirely. Our design uses
font size for the *width* fit, which forces the glyphs to the wrong height, and
then the vertical squash exists **only to undo the damage that coupling caused**.

That is the mechanism behind invariant 3's "four properties that fight each
other". Properties (b) and (c) are not naturally in tension; they are in tension
*because one constant is being asked to satisfy both*.

### Why we cannot simply adopt it

Our own `draw` comment already records the attempt: *"Fitting width by stretching
x instead exaggerates the gaps"* — and §1 explains exactly why that was fatal.
Stretching a **real** font horizontally scales its side bearings too, so a natural
0.1 em inter-glyph gap becomes 0.15 em at `Tz` 150% and crosses poppler's
`minWordBreakSpace`, splitting words. `accom plished` is that failure.

**Tesseract escapes this because its font is glyphless and fixed-pitch.** Every
character is exactly `fontsize/2` wide with no side bearings, so a uniform
horizontal stretch creates no intra-word gaps for an extractor to find. The
glyphless font is not a detail of their design; it is what makes the two-knob
architecture safe.

So the real option is a package — **glyphless fixed-pitch font + `Tz` width fit +
no vertical squash** — and it is written up with its costs in `FEATURES.md`
rather than started here.

### The hypothesis this research was meant to test, and its refutation

The question was: *would per-word runs with real spaces make properties (a) and
(d) structurally impossible to violate, retiring C18, C20, R81, R82 and A1.4 as a
class?*

**No, and the evidence is unusually direct.** Tesseract has emitted real spaces
between every pair of words since April 2019. Seven years later OCRmyPDF's own
documentation still warns that Tesseract's layer *"mightrunseveralwordstogether"*
in macOS Preview `[observational]`. Their diagnosis: the space's **drawn
position** overlaps the neighbouring word boxes, so a geometric extractor
"accurately reports what it sees".

And the fix for *that* has been tried and reverted upstream. OCRmyPDF shipped a
version that gave the space its own `Tz` sized to the real inter-word gap — the
design that would close property (d) — and backed it out in March 2026 because
words far apart in tables produced 300–500% horizontal scaling `[source]`.

**So the class does not retire.** What we have been doing — hold the gap open
deliberately, with a constant — is what both upstream implementations settled on
too, minus the derivation. We now have the derivation.

One correction to our own record while we are here: **the 64% figure that
justified per-line runs is confounded.** It measured another tool's per-word
output *with no space characters*, which is the pre-2019 Tesseract design whose
documented failure is exactly `EXPERIENCEANDRELATIVITY59componentsof`. It does
not establish that per-word runs are worse; it establishes that per-word runs
without spaces are worse. Re-run it before citing it again.

## 3. The crop box through `qpdf --overlay`: C23's refusal was wrong

`[measured]` — this section changed the code the same day it was written.

C23 shipped with a route fallback: a document hiding part of its sheet behind a
crop box did not take the JBIG2 route at all, at a measured **2.26x** in bytes on
16 of 233 corpus documents. The entry refused the alternative — editing the
merged file afterwards — on the grounds that it needed `qpdf --qdf`, a second
binary (`fix-qdf`), and hand-edited page dictionaries.

**That refusal was made without reading qpdf's option list properly.**
`--update-from-json` (qpdf 11+, JSON v2) applies a structured patch to an
existing PDF, leaves every stream alone, and needs no second binary:

```
qpdf merged.pdf --json=2 --json-stream-data=none --json-key=pages   # page order
qpdf merged.pdf --json=2 --json-stream-data=none --json-key=qpdf    # the objects
… add /CropBox to the page objects …
qpdf merged.pdf --update-from-json=patch.json out.pdf
```

Measured on the one-page fixture: **7,391 → 7,414 bytes, `/JBIG2Decode` intact**,
and lifting the trim off the result still finds the ink outside the crop. On a
real corpus document, `Canby_1929`: **91,595 bytes with compression against
206,002 on the Flate fallback** — the crop box now costs **477 bytes instead of
114,884**, and all 16 trimmed documents still display exactly what their sources
displayed (42 pages, 0 differing).

`--json-stream-data=none` is what makes it affordable: the JSON is proportional
to the file's *structure*, not its images.

### The trap, and it is a bad one

**`--update-from-json` replaces an object; it does not merge into one.** A patch
carrying only `/CropBox` for a page produces a page with *only* a crop box:
measured, **7,391 bytes became 391**, with `/Contents` and the image gone — and
`qpdf --check` reported the file healthy. Page count cannot see it either.

That is a content-destroying edit that passes every cheap verification, which is
invariant 1's nightmare. `JBIG2.setCropBoxes` is built around it: the page
dictionary is **read back from qpdf's own serialisation and handed straight back
with one key added** — the function never authors a page dictionary — and the
result is verified by comparing every page's content and image object lists
before it is allowed to replace anything.

## 4. What nobody upstream has measured, and we now can

Every PDFKit datapoint in six years of Tesseract and OCRmyPDF discussion is a
screenshot or an eyeballed copy-paste `[observational]`. Nobody has run a
controlled measurement against it — and PDFKit is Preview, Quick Look, Spotlight
and every macOS app that reads a PDF, which is the whole audience for this app.

We have two instruments that do: `Tools/score-run-width` (property (c), and the
ceiling that fights it) and `score-line-separation`'s `welded=` column (property
(d), counted directly). **That is the one place where this project is ahead of
the prior art rather than behind it**, and it is worth keeping in mind before
adopting an upstream design on upstream's say-so: their designs are tuned against
poppler and pdf.js, which behave differently from the extractor our users have.

## 5. Not researched, and why

- **R56 / R57 — the shape signal.** This is the next thread and it is the one
  with real prior art behind it (MRC segmentation, ITU-T T.44, DjVu's
  foreground/background separation since 1996, connected-component and
  stroke-width analysis). **Nothing in this file researches it** — what it does
  establish is that the problem is solved elsewhere and that the answer is a
  signal class none of the four refused rounds measured: every one of them used a
  luminance aggregate over a whole page, where the field uses the size, spacing
  and stroke geometry of connected components.

  The order of work is written out in `FEATURES.md` under *"The order of work for
  this, decided 2026-08-16"*, and its first two steps are deliberately cheaper
  than a build: write the acceptance test before the signal exists, then check
  whether `Flattener.inkOutsideText` — a structural signal already in the tree,
  currently asked only about background resolution — separates the two fixtures.
  That second one is an **unverified hypothesis**, recorded so the next person
  tests it rather than believes it.
- **C24 — `largestImage` reading a shared `/Resources`.** How `pdfimages` and
  mutool attribute images to pages would probably settle it. Not looked at.
- **A2.4, A13.4, and the checks that could not fail.** Ours. No prior art will
  help, and none was sought.
