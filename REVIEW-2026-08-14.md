### ~~A1.1 · Words weld again~~ — FIXED, `BUGS.md` R82 *(after A1.2/R81, as this entry required; 17 welds fixed and 0 created, and the predicted 113-sliver cost measured at 114 with R81's guard removed and 2 with it in)*

> **Verified independently, with corrections.** A second agent built its own instrument —
> exact segmentation of the extracted string with every character attributed to the run that
> drew it, cross-checked against the qdf-decompressed **content stream** (run geometry
> recomputed from the embedded font's own `/Widths`), poppler, each source's publisher OCR
> layer, and rendered crops.
>
> **What survives.** The count reproduces (32 welds / 24 in band vs 31 / 24), the cited pairs
> reproduce to the digit, the space really is absent from the content stream, and the gate is
> **causal** — 0.4 → 1.0 drops missing-gap welds 17 → 3. Severity measured: `findString` finds
> each word alone in 17/17 cases and the two-word phrase in **0/17**.
>
> **What does not.** "31 welded *word pairs*" overstates it. Of 13 adjudicable cases only **6
> are genuinely adjacent words on one visual line**; **7 are cross-column pairs, or a headline
> against a body line in another column** (one at 16.9 pt offset), where the predicate is
> *right* to refuse and a line break is the correct output. And **"PDFKit's line grouping is
> ~8 pt looser" was the first reviewer's own filter constant** reported as a property of
> PDFKit — on real pages PDFKit is not a function of baseline distance at all: of 1,472
> same-baseline adjacent pairs, 245 got a newline and 1,216 a space. `reserveEms`'s premise is
> shakier than assumed too: two welds had a drawn gap of *exactly* 0.25 em and PDFKit welded
> anyway, while three pairs with **negative** gaps got a space. Poppler welds only 3 of 17, so
> this is largely PDFKit-specific — which still matters, because PDFKit is Preview, Quick Look
> and copy-paste.
>
> **Real severity:** roughly **0.3 genuinely fused word pairs per dense newspaper page** (~6
> in 27,000 words). Single-word search unaffected; phrase search across the join and
> copy-paste corrupted.
>
> **The fix direction must change, and this is the valuable part.** The two options the first
> pass offered in one sentence are not equivalent, and both were measured:
>
> | variant | welds total / missing-gap | frags <15% of box | line-end selectable | overlapping pairs |
> |---|---|---|---|---|
> | shipped (0.4, `min`) | 60 / 17 | 30 | **96.4%** | 7 |
> | 0.4→1.0 both directions | 151 / 3 | 1022 | 71.1% | **38** |
> | reserve-only predicate at 1.0 | 130 / 3 | 1022 | 72.1% | 7 |
> | **reserve-only, `max` height, 0.4** | **55 / 5** | 113 | **94.7%** | 7 |
>
> A separate looser predicate *does* protect `headroom` (overlaps stay at 7 — that half of the
> warning was right), but it takes fragments drawn under 15% of their box from 30 to **1,022**
> and line-end selectability to 71%, which is the number `minimumVertical`'s calibration exists
> to escape — and **total welds get worse**, because slivers themselves provoke PDFKit
> block-joins. **Only the `max`-height variant is viable, and it still triples the sliver
> population, so it cannot ship before A1.2 is fixed.**

**31 welded word pairs across 21 real newspaper pages**, read back out of the composed
file with PDFKit. `ity`+`companies`, `female`+`member`, `Greece`+`(AP)_The`. This is C18's
symptom — `valuablestudy` — returned for a class of cases.

**Mechanism.** `reserveEms` (the constant that holds property (d) open) can only act
through `rightLimit`, and `rightLimit` only considers a neighbour that `isSameVisualLine`
accepts: baselines within `sameLineBaselineFraction` (0.4) × **min**(a.height, b.height).
The `min` is deliberate — C20 chose it so a tall display numeral cannot claim a body line
two rows away — but it means a pair where one fragment is short gets a tolerance of only
1.4–2.1 pt, while **PDFKit's own line grouping is far looser (~8 pt)**. In the band
between the two, no reserve is opened, the run is drawn to its full box width, and the
words weld. `headroom` does not cover it either: side-by-side fragments have no horizontal
overlap, so its test skips them.

Synthetic boundary, verified: two 9 pt fragments, gap ≤ 2 pt, baseline offset **3.7 pt**
against a tolerance of 3.6 → `the valuablestudy of it`. At 3.5 pt → correct. Setting
`sameLineBaselineFraction = 1.0` fixes every welded case in the sweep, which identifies
the gate as the cause.

**Do not simply raise the constant.** It is shared with `headroom` on purpose (C20 unified
them), and loosening it globally makes `headroom` skip real vertical neighbours — which is
the overlap defect C20 existed to fix. The reserve direction needs its own, looser
predicate, or `max` height for that direction only. **All four invariant-3 probes must be
re-run**, and nothing in the suite currently covers this band: `mutate.py` kills
`const/sameLineBaselineFraction` only with a "the calibrated value is 0.4" pin.

### ~~A2.1 · `publish` cannot replace an existing file on another volume~~ — FIXED, `BUGS.md` R59

`publish` uses `replaceItemAt(output, withItemAt: staged)` when the destination exists, and
`staged` is always in `NSTemporaryDirectory()` — the boot volume. `replaceItemAt` requires
both items on **one** volume and returns POSIX 18 `EXDEV` otherwise. The `else` branch
(`moveItem`) is fine, because Foundation copies across devices. So **the first run to an
external drive or network share succeeds and every later run over the same output fails**:

```
pass 1: succeeded   901054 bytes, 3 pages
pass 2: failed      "The file “Stiglitz.ocr.pdf” couldn’t be saved in the folder “pubtest”."
```

Verified against the real `makeSearchablePDF` with the output on a mounted volume, on both
HFS+ and APFS. Trigger: output folder on any non-boot volume — or *Save beside each
original* with the originals there — plus an output already present. Correct a setting,
press Start again, and every file in the batch fails with a message that names neither the
cause nor a remedy. Invariant 2 holds (the old file survives; nothing partial is written),
so this is total failure rather than content loss. The same applies to *Use Existing Text*;
plain Extract Text escapes it because it writes atomically to the target.

`Sources/Model.swift:1302-1309`.

### ~~A3.1 · The MRC memory accounting is wrong~~ — FIXED, `BUGS.md` R83 *(analytically, not by a fresh RSS campaign — the verifier's own point was that RSS is the wrong instrument here; the colour route gained a bound of its own, derived rather than chosen)*

> **Read this first.** An adversarial verifier attacked this finding and was right to. The
> **omission is real** and `measuredMRCBytesPerPixel = 8.0` **is wrong**, but the 26.5 and
> 30.5 B/px figures below are a **memory-retention artifact**, and the conclusion drawn
> from them was inverted.
>
> **Why the numbers were wrong.** `ru_maxrss` is a high-water mark, and libmalloc keeps
> freed large blocks mapped *and dirty* — so over a multi-phase function it reads as a **sum
> of distinct-size peaks rather than a maximum**. The verifier's control settles it: two
> 8 B/px phases with a `free` between them read **16.38 B/px** by `ru_maxrss` and **8.00**

> `textRegionMask` and `inverse` exist, so the integral images are never alive with them.
> Measured on one real page: `renderGrey + sauvolaMask` live peak **1,181.8 MB**; the whole
> grey `mrcLayers` live peak **1,181.8 MB** — identical to the byte.

> **What survives.** `sauvolaMask`'s two `(w+1)(h+1)` `[Double]` integral images (16 B/px)
> are genuinely absent from the enumeration, and they are the peak: 1 + 8 + 8 + 1 = **18.005

> an accurate description of the `fillHoles` phase — it simply is not the maximum. So the
> constant is wrong by ~2.3x, not 3.3x.
>
> **The emphasis was inverted.** Matched instruments on the corpus's largest page (64.84 MP):

> worst at `PhotoDetail.maximum` (42.4 B/px by peak footprint). Colour is the finding.

> not their sum); define the unit and re-measure both sides in it; give the **colour** route

### ~~A3.2 · `textRegionMask` traps on a non-finite word box, uncatchably~~ — FIXED, `BUGS.md` R61

Four bare `Int((b.x ± padX) * Double(w))` conversions, where `Flattener.safeInt` exists in
this same file with the comment "the conversion is never safe on its own (R24)". Exit
**133/SIGTRAP** for `.nan`, `.infinity`, `1e300` and `width = 1e19`; the finite control
returns normally. Uncatchable, so it takes the whole batch.

The ordering is the point: these boxes reach `mrcLayers` **before** `SearchableWriter.compose`
runs, and `compose`'s guard against non-finite coordinates — verified sound in area 1 — is
downstream of the crash. The one place that refuses these values cannot protect the one

## Area 4 — security and privacy (cross-cutting)

Threat model stated up front, because it decides severity: a local, unsandboxed,

### ~~A4.1 · The run report contains excerpts of the user's document text~~ — FIXED, `BUGS.md` R64

`Model.swift:1789-1798` builds the unplaced-lines failure message out of the recognised

### ~~A5.1 · Retry Failed publishes over a file the same batch deliberately kept off~~ — FIXED, `BUGS.md` R60

**The most severe finding in this sweep.** `uniqueOutputs` seeds `claimed` with the batch's
own inputs, precisely so that re-running a folder containing a previous run's results cannot
claim a name another worker is reading. `retryFailures` narrows `files` to the failures, and
`run` re-resolves outputs from that narrowed list — **so the sibling that was doing the
protecting is gone, and the retry claims the name that was reserved away from it.**

Sequence A, run end to end:

```
dir/scan.ocr.pdf   13,006 bytes, text "PRECIOUS ORIGINAL from the previous run"
dir/scan.pdf       arrives truncated
drop dir, save beside each original, Start
  scan.ocr.pdf -> dir/scan.ocr.ocr.pdf      OK
  scan.pdf                                  FAILS, unreadable
dir/scan.ocr.pdf still says PRECIOUS        <- uniqueOutputs did its job
replace dir/scan.pdf with a readable scan, press Retry Failed
  scan.pdf -> dir/scan.ocr.pdf              OK
dir/scan.ocr.pdf   7,268 bytes, "REPLACEMENT SCAN"   <- the user's file is gone
```

Sequence B is the ordinary one-output-folder configuration: two inputs sharing a base name
in different folders, the second fails, and the retry overwrites the first's published
output. Run 1's log **and its run report** both name that path as the first input's result;
the retry's log says nothing, and `renamedOutputs` is empty on a retry so even the "(renamed;
another input claimed that name)" note is absent.

Any per-file failure that does not recur triggers it: a truncated download, an encrypted PDF
once the password is entered, a full or unmounted destination — **or A2.1's `EXDEV`**, which
means the bug I fixed this morning was a trigger for this one. `publish` is atomic; it is
atomic onto the wrong file. Invariant 1 and the spirit of invariant 2 both fail.

**Fix direction, and the obvious version of it does not work — established by trying it.**
Seeding `claimed` with the retried attempt's `resolvedOutputs` is *not* sufficient, and a
first attempt at exactly that failed its own test:

```
FAIL  a retry that carries the first attempt's outputs keeps its own path — scan.ocr.pdf
FAIL  a retry cannot publish over another input's finished output — scan 3.ocr.pdf vs a=scan.ocr.pdf
```

The reason is the whole point of the defect: in sequence A the protected path
(`dir/scan.ocr.pdf`) was an **input** of the first attempt, not one of its outputs, so
carrying outputs forward does not re-reserve it. And in sequence B carrying outputs forward
over-reserves — the retried file's *own* previous slot is in that set, so it is pushed to a
*third* name (`scan 3.ocr.pdf`) rather than reusing `scan 2.ocr.pdf`, which is a second,
quieter bug: every retry would rename the output again.

So a correct fix has to carry forward **both** the earlier attempt's inputs and its outputs,
**and** exempt the file being retried from its own earlier claim. The state also has to
accumulate across *repeated* retries (a set of paths, not a map keyed by input, or the third
attempt forgets the first's) and be cleared whenever the user changes the file list — through
**both** `add` overloads, `remove` and `clearFiles`, which is §4b's sweep on the fix itself.

§4b more broadly: anything that runs a *subset* of a previous batch has this shape.

## Area 13 — `Recogniser.swift` + `Helper/main.swift`: **sound**, with one real defect

**The protocol's central claims survive being attacked.** No route loses a page, no route returns

### ~~A13.1 · An embedded NUL in *Languages* or *Custom words* aborts the app uncatchably~~ — FIXED, `BUGS.md` R73 *(and refined: a NUL in the final position does not abort, it silently truncates)*

`Process.arguments` goes through `fileSystemRepresentation`, which **raises
`NSInvalidArgumentException` for a string containing U+0000**. An Objective-C exception is not a
Swift error, so the `do/catch` around `process.run()` does not catch it: SIGABRT, exit 134.

```
customWords has a NUL: false -> succeeded, published
customWords has a NUL: true  -> NSInvalidArgumentException, libc++abi: terminating (134)
```

`report` is never called and `fellBack` is never called. **The asymmetry is exact**: the same
snapshot recognises perfectly *in-process*, and `useHelper` is `helperIsWorthIt` — so **a one-file
batch works and a two-file batch kills the app.** It also **persists**: `UserDefaults` round-trips
the NUL, so every multi-file batch aborts until the user finds and clears an invisible character
in a text field.

Fuzzed 16 candidates in child processes: **only NUL does this.** `U+0085`, `U+2028`, `U+FFFF`, a
bare CR, ZWJ emoji, an RTL override and 256 KB arguments all launch; a ≥1 MB list gives a
*catchable* Swift error that correctly falls back. **§4b makes it a single-site fix**: of five
`Process.arguments` in `Sources/`, the other four carry only paths and constants — and A4.3's
password fix incidentally removed the second free-text exposure.

Reachability is **low and unproven at the UI** — typing a NUL is impossible, pasting is the route,
and AppKit's paste filtering could not be tested without a running app. Reported anyway because
this is the one thing the file promises cannot happen: `HelperFailure`'s docstring says "every case
falls back", `helperName` says "the worst a broken helper can cost is time", and ARCHITECTURE says
"the helper is never authoritative about failure". All three are false for the *launch*, and
`makeSearchablePDF`'s "the `report` callback is called exactly once per file" is broken. One guard
on the two raw fields, the same shape as the `unusablePaths` guard 36 lines above.

### ~~A13.2 · A document Vision reads nothing from publishes as a success with an empty message~~ — FIXED, `BUGS.md` R74

### ~~A13.3 · The `unusablePaths` guard checks `"\n"` and misses `"\r"`~~ — FIXED, `BUGS.md` R75
