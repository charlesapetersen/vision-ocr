STEP 3 — DO IT. The non-negotiables, from CLAUDE.md and CONTRIBUTING.md:
  * **Your own worktree, on an `auto/` branch.** Never work in the primary checkout — the owner has live
    interactive sessions there, and one of them may be mid-commit.
        stamp="$(date +%Y%m%d-%H%M%S)-$$"
        git worktree add "/private/tmp/vo-$stamp" -b "auto/$stamp" && cd "/private/tmp/vo-$stamp"
    The `auto/` prefix is load-bearing: the daemon's housekeeping GCs `auto/*` worktrees once they are
    provably pushed AND clean, and touches nothing else. The owner's own `work/*` worktrees are never
    reclaimed. Confirm you are in your own worktree before editing anything.
  * **⛔ NEVER RUN TWO TEST SUITES AT ONCE — in any two worktrees.** `build/tests` has no bundle identifier,
    so `UserDefaults.standard` lands in `~/Library/Preferences/tests.plist` keyed by the process name, and
    every worktree shares that ONE file. A second suite's `resetPrefs()` wipes the first one's settings
    mid-run: measured 882/883 → 877/879, with failures unrelated to any change. That is the worst kind of
    result — evidence that is WRONG rather than absent. So always:
        ops/autonomous/test-lock.sh run --label session -- ./run_tests.sh
    This includes suites started by any subagent you launch. To check who holds it:
    `ops/autonomous/test-lock.sh status`. If it says a suite is running, WAIT — that is correct behaviour,
    not a fault. And when you need to know whether a suite is live, it is `pgrep -x tests`, never
    `pgrep -f build/tests`: the `-f` form matches every waiter including your own shell, and four such loops
    once sat waiting on each other while nothing ran.
  * **A failing test FIRST, and watch it fail.** CONTRIBUTING records three tests that passed against a
    deliberately reintroduced bug. A fix without a test that fails without it is not finished. Tests are
    `check(...)` calls in `Tests/main.swift`.
  * **A sibling sweep**, and the answer goes in the commit message: grep for who else does this thing. Half
    this register's entries are one instance of a pattern that had several.
  * **A mutant** in `Tools/mutate.py` if you changed a constant or a guard, run scoped
    (`python3 Tools/mutate.py --only <substring>`), with the row appended to `Tools/mutation-log.tsv`.
    ⛔ **NEVER the full catalogue.** This line said "~70 minutes", which was arithmetic on a 2-4 minute
    suite. **Measured 2026-08-17 by the C24b campaign**: 2661-2719 s per mutant, so ~45 min each, over
    **89 mutants** (`--list` says 89 — every doc that said 84 predated the C24b five). The full
    catalogue is on the order of **65 HOURS**. Not a thing to start in a session.
    A SCOPED run costs a **baseline suite plus ~45 min per mutant**, and the baseline is a full run that
    is easy to forget: five mutants took **4h27m end to end**, against the "20-55 minutes" the tool
    printed before starting. Budget it like several commits, not like a check — and read the estimate the
    tool prints at startup, not any number written here.
    A **`Tools/fault-inject.sh` case** if you added an error branch.
    ⚠️ Do not edit `Sources/` while `mutate.py` is running. ⚠️ And `mutate.py` does NOT take the suite
    lock: check `ops/autonomous/test-lock.sh status` first. It will not yield to a health gate or a hook
    already mid-suite, and two suites at once corrupt both.
  * **Never write a real corpus.** `testdocs/` is 1.2 GB of third-party copyrighted PDFs that is not
    committed and cannot be regenerated without the owner's Zotero library. Read it; never write it. Test
    output goes to `mktemp` scratch. File safety beats getting it done.
  * **NEVER `git commit --no-verify`** (it is denied at the tool layer too). The pre-commit hook running the
    suite is the only thing between this run and pushing untested code. If the suite fails, fix it or stop.
  * **Never `--force` past a git or tool refusal** (`worktree remove`, `reset --hard`, `clean`, `branch -D`).
    A refusal means STOP and investigate: dirty files may be a parallel session's work.
  * The five **invariants** in CLAUDE.md §Invariants have each destroyed user content before. If you touch
    `SearchableWriter`, re-measure ALL FOUR text-layer properties — each has been broken by a fix to another.
  * Environment traps that have each cost real time: a **backgrounded shell has essentially no PATH** (use
    absolute paths; `basename`/`cut`/`timeout` fail silently); a **redirected suite log lags up to 4 KB**, so

    immediately** while the work runs orphaned; the volume is **case-insensitive**; corpus filenames contain
    spaces and **U+00A0** — glob, never retype.

STEP 4 — COMMIT, with the documents moving in the SAME commit.
  The hook will run the full suite on any commit touching
  `Sources/|Helper/|Tests/|Tools/|build.sh|run_tests.sh`; docs-only commits are free.
  ⚠️ **A COMMIT COSTS ABOUT FORTY MINUTES, NOT FOUR.** This line said "2-4 minutes" until 2026-08-16 and was
  wrong by an order of magnitude. The suite was then timed end to end: **39m30s** — lock acquired 20:29:23,
  released 21:08:53, 1137/1137 with no skips; swiftc 1m47s of it, the `tests` binary the other 37m43s, at
  ~96% of one core throughout. The health gate that wraps it measured 44m53s. Plan the whole item around
  that, and note that you pay it TWICE if you run the suite yourself before committing — the hook does not
  know you just ran it. If you have already run a green suite and changed nothing since, going straight to
  the commit and letting the HOOK be your suite run is the cheaper order.
  ⛔ **NEVER END YOUR TURN WITH A COMMIT STILL IN FLIGHT.** This is how the run stalled on 2026-08-16: a
  95-minute session did the whole of C24b, went green 1137/1137, backgrounded `git commit`, wrote itself a
  hand-off saying the work was done — and ended its turn (`stop_reason: end_turn`, rc=0, $15.10 of $20, no
  watchdog and no cap involved). Ending the turn KILLS every background task, so the hook died at
  `Terminated: 15` partway through its suite, nothing landed, and the daemon correctly logged "advanced
  nothing". Two sessions and about three hours bought one commit's worth of nothing.

  ⛔ **AND YOU CANNOT JUST RUN IT IN THE FOREGROUND — THE BASH TOOL CAPS AT 10 MINUTES.** `timeout` maxes
  out at 600000 ms, so a foreground `git commit` on a ~40 minute hook is killed at 10 minutes, every time,
  with `Exit code 143 Command timed out after 10m 0s`. Measured 2026-08-16 21:31→21:41: a session tried
  exactly that, lost ten minutes of suite, and had to start the whole hook again. So the ONLY working
  shape is detached-plus-poll:

      cd <your worktree> && export PATH="/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin:$PATH"
      git commit -F /tmp/<your-msg>.txt > /tmp/<your>-commit.log 2>&1 &

  Write the message to a FILE first — a heredoc into a backgrounded command is a good way to lose it — and
  set PATH explicitly, because a backgrounded shell here has essentially none.

  ⚠️ **THEN POLL ON `HEAD`, NOT ON `pgrep -x tests`.** The hook type-checks the staged tools and compiles
  for about two minutes BEFORE the `tests` binary exists, so `pgrep -x tests` is false at the start of a
  perfectly healthy hook and a poll keyed on it reports "hook finished" almost immediately. The same
  session made that mistake in the same hour and had to catch itself. The condition that means what you
  want is the sha moving:

      before=$(git log -1 --format=%h)
      for i in $(seq 1 300); do
        now=$(git log -1 --format=%h)
        [ "$now" != "$before" ] && { echo "landed: $now"; break; }
        /usr/bin/grep -qE 'TESTS FAILED|commit refused' /tmp/<your>-commit.log && { echo "REFUSED"; break; }
        /bin/sleep 10
      done

  Each `seq`/`sleep 10` batch is well under the 10-minute cap, so run several back to back until one of the
  two conditions fires. Poll to completion before you stop — "I asked for it" is not "it landed".

  ⛔ **NEVER END YOUR TURN WITH A COMMIT STILL IN FLIGHT.** Ending a turn KILLS every background task, which
  is how the 95-minute session above lost everything. Before STEP 6, PROVE the commit exists:
  `git log -1 --format=%H` must differ from the sha you started from, and `git status --porcelain` must be
  clean. If it does not, say so in RUN.md's SESSION LOG in those words — your staged work survives in the
  worktree and the next session can finish it, but only if your log says the commit never landed instead of
  implying it did.

    * the `ops/autonomous/QUEUE.md` checkbox — but ONLY on the final, completing commit. A checkpoint commit

VERIFICATION DISCIPLINE — this project's culture, and it is stricter than most:
  * **State plainly whether a finding was verified by running code or only reasoned about.** Never report a
    change as working without the suite passing. "An entry without evidence is a rumour."
  * **When a measurement is surprising, suspect the instrument first.** Several "confirmed" findings here
    were artifacts: `difflib` autojunk on repetitive text, a glob matching unrelated files, ImageMagick's
    `AE` exceeding the pixel count, a probe counting short lines as failures. Ten checks in this register's
    history *could not fail* — they were written, looked green, and asserted nothing.
  * Prefer `Edit` over scripted text-slicing on source files: an over-broad Python slice once deleted four
    functions from `Model.swift`.
  * Do not invent numbers. If you did not measure it, say so.
